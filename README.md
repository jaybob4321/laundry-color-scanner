# Laundry Color Scanner

A mobile-first Progressive Web App. Point your phone camera at a piece of clothing, or upload a photo, and it tells you:

- the garment's **common color name** (from 57 clothing reference colors),
- a **laundry sorting group** (Whites, Lights, Darks, Reds / Pinks, Blues, Greens, Yellows / Oranges, Browns / Beiges, Grays, Multicolor, Other),
- a **heuristic match confidence** with High / Moderate / Low labels,
- the **three closest reference colors**, plus HEX, RGB and Lab values.

Everything runs **on the device**. Photos are never uploaded, never stored, and the detector needs no network or API key. Once installed, it works offline.

**Live app:** <https://jaybob4321.github.io/laundry-color-scanner/> — open it on your phone and allow camera access. To install, use **Add to Home Screen** (iPhone: Share → Add to Home Screen; Android: the Install prompt).

> Color sorting suggestion only. Follow the care label; wash new or bleeding items separately.

This is one shared project. [docs/BLUEPRINT.md](docs/BLUEPRINT.md) (technical design by ChatGPT) is authoritative for behavior. [spec/colors.json](spec/colors.json) is authoritative for the seed colors. [docs/IMPLEMENTATION-NOTES.md](docs/IMPLEMENTATION-NOTES.md) records implementation status, measured performance and every deviation from the blueprint.

## Running it

Requirements: Node.js 20+. There are no runtime dependencies. The only dev dependency is `playwright-core`, for browser tests.

```bash
npm install
```

```bash
npm start
```

Then open <http://localhost:8080/>. Localhost counts as a secure context, so the camera and offline mode work there on a desktop with a webcam. Without a camera, use **Upload Photo**.

| Command | What it does |
| --- | --- |
| `npm start` | Static dev server on port 8080 (`--port`, `--host 0.0.0.0` for LAN). |
| `npm run build` | Copies `spec/colors.json` → `data/colors.json` and regenerates the service-worker precache list and version hash. **Run after every change**, or offline users keep the old version. |
| `npm run check` | Verifies the build outputs are current (the unit tests check this too). |
| `npm test` | Unit + integration tests (Node test runner). |
| `npm run test:e2e` | Browser tests with the installed **Microsoft Edge** (`E2E_CHANNEL=chrome` for Chrome, `E2E_HEADED=1` to watch). |
| `npm run bench` | Detector timing per stage (p50/p95). |
| `npm run icons` | Re-renders the PNG icons. |
| `npm run profiles -- manifest.json` | Builds reference profiles from curated photos (see below). |

**On a phone:** browsers only allow camera access over HTTPS, so serve the folder from any static HTTPS host (GitHub Pages, Netlify, Cloudflare Pages…) or through an HTTPS tunnel to `npm start`. The app uses only relative paths, so hosting in a subdirectory works.

**Publishing updates (GitHub Pages).** The live app is served straight from the `main` branch root; `.nojekyll` makes Pages serve files as-is. After changing anything:

1. Run `npm run build` (refreshes the offline cache version), then `npm test`.
2. Commit and `git push`. Pages redeploys in about a minute.
3. Phones that already have the app show **Update available → Reload to update** on Home.

**Development switches** (only while `debugAvailable` is true in [src/app-config.js](src/app-config.js)):

- `?debug=1` shows the developer panel on results. It's also a toggle in Settings.
- `?nosw=1` runs without the service worker, so edits show up on reload.
- `?ai=mock` enables a local mock AI provider for testing the consent flow. It sends nothing.

For production, set `debugAvailable: false`. That removes all three switches and the `window.__lcs` inspection hook.

## Using it

1. **Scan Clothing** opens the rear camera. Fill the white target with fabric (not skin or background) and tap the shutter. The target is 60% of the shorter screen side. A live hint says “Ready” or suggests reframing (glare, too dark). **Flash** appears only when the camera supports a torch.
2. **Upload Photo** opens the photo in *Adjust target*. Drag the box, or resize it from its corner, arrow keys, Shift + arrow keys, or number fields. Then tap **Analyze**.
3. **Results** show the swatch, name, laundry group, confidence, closest matches and guidance.
   - **Adjust** re-crops the same photo.
   - **Correct Result** saves what the color really was.
   - **Add Reference** saves this scan as a personal reference color.
   - **Scan Another** starts over.

## Architecture

Plain HTML, CSS and native ES modules. There's no framework, no bundler, no remote fonts and no analytics. Numeric work runs in one module Web Worker, so the camera and UI stay responsive.

```text
index.html, styles/app.css         UI shell (all screens as static, accessible markup)
manifest.webmanifest, sw.js        PWA manifest and service worker (precache generated by npm run build)
assets/icons/                      generated PNG icons (any, maskable, apple-touch)
data/colors.json                   the reference color database (copy of spec/colors.json)
data/detector-config.json          every detector threshold, versioned (configVersion)
data/reference-profiles.json       curator-approved numeric profiles (empty to start)

src/app.js                         state machine: Home → Camera | Upload → Crop/Analyze → Results → Correction/Reference
src/camera.js                      getUserMedia (rear camera, no microphone), torch, error classification
src/image-input.js                 EXIF-aware, color-managed decode into sRGB canvases; ROI pixel extraction
src/geometry.js                    object-fit cover/contain overlay → normalized source ROI
src/detector-client.js             worker client: one active + one pending job, stale replies ignored, main-thread fallback
src/worker/detector.worker.js      runs the pipeline off the main thread
src/detection/pipeline.js          the detection pipeline (pure; also used by tests and scripts)
src/detection/{sampling,quality,pattern,calibration,confidence}.js
src/color/{srgb-lab,delta-e-2000,cluster,match}.js
src/grouping.js                    ordered laundry-group rules, overrides, boundary flags
src/references.js                  palette validation/index/search, reference-profile quality gates
src/schema.js                      runtime validation of stored and imported records
src/storage.js, src/data-transfer.js   IndexedDB persistence; versioned export/import
src/ai/{provider-contract,client}.js   optional AI fallback interface (disabled)
src/ui/*.js                        screens, region editor, color picker, debug view, user-facing copy
scripts/                           build, dev server, icons, benchmark, reference-profile builder
tests/{unit,integration,e2e,fixtures}
```

The file layout follows blueprint §2. The main additions are `detection/sampling.js` and `detection/pattern.js`, split out of the pipeline, and a `ui/` folder instead of a single `app.js`.

## How color detection works

1. **Crop.** Only the target region is analyzed, never the whole photo. Coordinates are mapped from the on-screen overlay to real image pixels, including `object-fit: cover` cropping, and stored normalized (0–1). The crop is at most 1024 px on its longest side.
2. **Sample.** 4,096 single-pixel samples come from a 64×64 grid, each jittered deterministically inside its cell. Samples are never cell averages, so thin black/white stripes stay black and white instead of blurring to gray. Transparent pixels (alpha < 250) are skipped. Near-black and near-white fractions are recorded as quality indicators, but those pixels are **kept**: deleting them would delete real black or white fabric.
3. **Convert.** sRGB → linear RGB (256-entry lookup table) → XYZ → **CIELAB (D65, 2°)**. This is not CSS `lab()`, which is D50.
4. **Cluster.** Deterministic k-means runs for k = 1…5 on the unaveraged Lab samples, with two farthest-point initializations and at most 12 iterations. The number of clusters minimizes `N·ln(max(SSE/N,1)) + 4k·ln N`. Clusters whose representatives are closer than **6 ΔE00** merge. Each cluster's *representative* is a real sample nearest its median, so different clusters are never averaged into a made-up color. Small isolated highlight/shadow specks don't influence representatives.
5. **Match.** Each representative is compared with every reference color using **CIEDE2000**. The implementation matches all 34 published Sharma reference pairs to within 0.0001. The distance method is pluggable (`matching.distanceMethod`). The top 3 are returned with their distances. A best distance above 18 means “Unrecognized color”; 10–18 is flagged as uncertain.
6. **Group.** Ordered rules run on the *measured* color (see Laundry groups below).
7. **Confidence.** A heuristic score combines fit, margin and stability (see Confidence below).

A second jittered sample (seed 2) is clustered too. It measures stability and must agree before a result is called Multicolor.

## Adding reference colors

All reference colors live in one place. **Don't** add colors in application code.

1. Edit the table in [spec/generate-colors.mjs](spec/generate-colors.mjs) (`Name|HEX|family|alias`). The family is one of neutral, blue, green, yellow, orange, brown, red, purple.
2. `node spec/generate-colors.mjs` regenerates [spec/colors.json](spec/colors.json) with computed RGB, Lab and default group.
3. `npm run build` copies it to `data/colors.json`, then `npm test`. The tests verify every entry's RGB/Lab and that the grouping rules reproduce its default group.
4. Bump `paletteVersion` when names or anchors change. Every result records the palette version.

Each entry has `id, name, hex, rgb, lab, laundryGroup, family, aliases`. Aliases are search labels (e.g. “Grey”, “Wine”), not extra match candidates.

**Reference images.** Photos are preprocessed into numeric profiles once. They are never compared image-to-image during a scan.

- **In the app:** on a result, tap **Add Reference**, choose the true color and the lighting.
  - The scan must pass quality gates: one color covering at least 85% of the target, an even color, and almost no clipping.
  - Known lighting (neutral, or calibrated with a white reference) and a result within 12 ΔE00 of the anchor produce an **enabled** profile.
  - Otherwise the profile is saved as **pending** and isn't used.
  - Enabled profiles compete in matching with a +2 distance penalty.
- **Curated set:** list photos in a manifest and run `npm run profiles -- manifest.json`. Photos must be plain sRGB PNGs; color-managed or EXIF-rotated files are rejected with a reason. Every profile comes out **pending**. A curator approves it by setting `"status": "approved"` in `data/reference-profiles.json`. Run `npm run build` afterwards. The report (`reference-report.json`) lists accepted, patterned and rejected photos. Manifest format:

```json
{ "schemaVersion": 1, "records": [ {
  "id": "navy-tee-01", "image": "photos/navy-tee-01.png", "colorId": "navy",
  "garmentRoi": { "x": 0.3, "y": 0.2, "width": 0.4, "height": 0.5 },
  "neutralRoi": { "x": 0.02, "y": 0.8, "width": 0.12, "height": 0.15 },
  "lighting": "calibrated", "license": "CC0-1.0", "provenance": "Photographed by …, 2026-09-25"
} ] }
```

## Laundry groups

Stable IDs: `whites, lights, darks, reds-pinks, blues, greens, yellows-oranges, browns-beiges, grays, multicolor, other`. Rules run in order on the measured Lab color:

1. Confirmed multicolor → **Multicolor**
2. Unrecognized or ambiguous → **Other** (“needs review”)
3. Your per-color override (Settings)
4. L ≥ 94 and chroma ≤ 4 → **Whites**
5. L < 38 → **Darks** (navy, dark brown, burgundy…)
6. Red family → **Reds / Pinks** (including light pink)
7. L ≥ 75 → **Lights** (pale blue, cream, beige…)
8. By family: neutral → Grays, blue → Blues, green → Greens, yellow/orange → Yellows / Oranges, brown → Browns / Beiges, purple → Other

In **Settings** you can move whole families (e.g. purples → Darks) or single colors. Changes apply to new scans only. Saved results keep the grouping version they were made with.

If the measurement sits within 2 L (or 1 chroma unit) of a threshold, *and* crossing it would change the group, the result says so (“Close to the boundary with Grays”). Its sorting confidence is then capped at 60.

## Calibration (optional)

Camera white balance varies, so a warm lamp can turn light gray into “beige”. There are two ways to correct it:

- **Same photo (preferred):** in *Adjust target*, tap **Add white reference**. Place the dashed box on a matte white or gray card lying beside the garment in the same light.
- **Live:** on the camera screen, tap **Calibrate**, aim at the card, and tap the yellow button. It applies to captures from the same camera session with the same flash state, for 2 minutes. It's cleared when the flash changes, the app goes to the background, or you leave the camera.

The card is checked before its gains are used. It must provide ≥ 256 samples, medians of 40–245, < 2% clipping, even lighting (MAD ≤ 0.03), and gains within 0.67–1.5. A colored card is rejected. Gains are applied in linear RGB and don't change exposure. If calibration would newly clip more than 5% of the garment, it's discarded, and the result says so.

Results show **Calibrated / Without calibration** for one-tap comparison, plus **Reset calibration**.

## Confidence

The percentage is **heuristic match confidence, not a probability of being right**: “Based on color similarity and image quality; lighting can change the result.”

```text
score = 100 × (.35 fit + .20 margin + .15 compactness + .15 stability + .15 quality)
```

- **fit:** closeness of the best reference.
- **margin:** gap to the next different color.
- **compactness:** how even the color is.
- **stability:** agreement with the second sample.
- **quality:** share of pure black or white pixels.

Caps are applied afterwards:

| Condition | Cap |
| --- | --- |
| Uncalibrated scan | 85 |
| Calibrated scan | 95 |
| More than 20% of samples near clipping | 65 |
| Best distance above 10 | 60 |
| Top two names within 1 ΔE00 | 55 |
| Multicolor | 85 |
| Possible shadow edge | 70 |
| Ambiguous pattern | 55 |
| Mixed colors | 60 |

Labels: **High** ≥ 80, **Moderate** 60–79, **Low** < 60. Low shows “Check result”.

**Sorting confidence** is computed separately, from the margin to the nearest color that would sort into a *different* group. It's shown when it differs by 15 or more points. For example, a garment can be 55% “Burgundy vs Maroon” yet 85% sure to be Darks.

## Multicolor detection

A result is **Multicolor** only when all three of these hold:

- **Colors differ:** at least two significant clusters (≥ 15% of the target each), at least 15 ΔE00 apart, together covering ≥ 70%.
- **Spatial evidence:** on a 128×128 map, the boundaries between colors are sharp (≥ 35% of boundary edges), or both colors are spread over ≥ 6 of 16 grid cells with ≥ 20% sharp edges.
- **Stability:** the second jittered sample agrees, with proportions within 10 points.

So 50% black / 50% white is **never averaged to gray**. It's Multicolor, with each area measured separately. The same goes for red/blue (never “purple”).

When the colors differ but the spatial evidence or agreement fails, the result is **“Pattern or shadow?”**: group Other, low confidence, and a suggestion to use flat, even light. Smooth shading doesn't produce a confident Multicolor. A cluster of 8–15% is reported as a *possible accent color*.

Percentages describe the sampled target, not the whole garment. They use largest-remainder rounding, so they sum to 100, and small leftovers are shown as “Other colors”.

## Corrections, privacy and local data

- **Correct Result** saves a structured record: the full original result with its metrics and versions, your corrected color/group/pattern, and an optional note. It's stored in IndexedDB on this device only. Corrections are evidence for improving the detector later (`usedForLearning: false`). They never change detection automatically and never alter the original result.
- **Settings → Your data:**
  - **Export** writes a versioned JSON file (no photos).
  - **Import** validates every record (5 MB and 5,000-record limits, duplicates skipped) and asks before merging.
  - **Delete all local data** clears everything.
- If storage is blocked (e.g. a private window), scanning still works and saving says “Could not save locally”.
- Normal scans make **no network requests with photo or pixel data**. The e2e suite checks this.

**Optional AI fallback.** An `AIColorProvider` interface exists but is **disabled** (no provider, no keys).

- If a same-origin proxy is configured later, **Review with AI** appears only for low-confidence or ambiguous scans.
- Before anything is sent, it shows the exact crop (re-encoded to ≤ 768 px without metadata) and the provider name, and asks for an explicit **Send**.
- The AI answer is validated, shown separately, and never replaces the local result or its confidence.
- API keys must never be put in browser code.

## PWA installation and offline behavior

- **Android / Chrome / Edge:** an **Install app** button appears on Home when the browser offers installation.
- **iPhone / iPad:** tap Share, then **Add to Home Screen**. The app shows this hint on iOS.
- Installation isn't required to scan.

After **one** successful online visit, the service worker has cached the complete app in one versioned cache: HTML, CSS, JS, worker, palette, config and icons. From then on, capture, upload, detection and corrections all work offline, and Home shows **Offline ready** once the cache has been verified. A first-ever visit can't work offline.

New versions download in the background. Home shows **Update available → Reload to update**, and an update never activates mid-scan. Old caches are deleted on activation. Photos, uploads and AI responses are never cached.

## Known limitations

- **Accuracy isn't yet validated on real garments.** Every threshold is an initial default from the blueprint. The held-out evaluation it describes (60+ garments, 3 lighting setups, 2 phones) hasn't been done, so the confidence numbers are heuristics, not measured accuracy.
- A camera can't measure fabric reflectance. Mixed lighting, strong color casts, fluorescent, metallic or iridescent fabrics, glare and clipped highlights can all mislead the detector. Calibration fixes a single even color cast only.
- The scan describes **only the target region**. It doesn't find garment edges, remove backgrounds, recognize fabric or read care labels.
- Very fine patterns below the image resolution may be reported as “Pattern or shadow?”, or look uniform. Hard shadows can look like a two-color pattern; they're flagged and capped at 70.
- Near-black and near-white garments are inherently ambiguous (navy vs black, white vs cream); the result shows alternatives instead of forcing one.
- HEIC photos only open where the browser supports them (Safari). Photos over 24 MP are rejected unless the browser can downscale while decoding.
- The camera needs HTTPS. Torch control depends on the device (usually Android Chrome only).
- Live calibration ends when you leave the camera screen, as the blueprint requires, so each new camera session needs recalibrating. Same-photo calibration has no such limit.
- The curated reference-photo builder reads plain sRGB PNGs only.
- The tests run on desktop Edge (Chromium). Real-device behavior on iOS Safari and Android Chrome (installation, background/resume, camera quirks) still needs manual verification (blueprint §17).
